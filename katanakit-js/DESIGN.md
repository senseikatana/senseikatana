# Design System: KatanaKit

## Overview

**Creative North Star: "The Technical Workshop"**

KatanaKit is a practical, modular toolkit. Its visual language prioritizes readable interfaces, explicit semantic states, and reusable scales over decorative treatment. The source SCSS palette is the design-token authority for the UI package; the documentation site inherits its separate light and dark surfaces from VitePress.

The amber and orange families are established palette options, not new runtime tokens: both already exist in `scss/_variables.scss`. This document makes their full scales visible in OKLCH alongside every other source palette. Values are converted from the existing HSL/HSLA source for documentation; the Sass source remains unchanged and authoritative for rendered colors.

**Key Characteristics:**

- Semantic, named color families with eleven shades (50–950).
- A compact UI kit built from purple primary actions, neutral surfaces, and clear status colors.
- Independent documentation-site colors with light and dark theme variants.

## Colors

The complete machine-readable color inventory is in the frontmatter above. Each value is written as OKLCH and corresponds to its source HSL/HSLA value after conversion and rounding; tokens are not changed in the source stylesheets. The `transparent` and `currentColor` Sass helpers are intentionally excluded because they are compositing/current-text keywords rather than fixed colors.

### Primary

- **Katana purple** (`purple-500`): palette anchor for the UI kit; buttons use `purple-600` with `purple-700` hover, and focus rings use `purple-500`.
- **Documentation indigo** (`docs-light-indigo-1` / `docs-dark-indigo-1`): VitePress brand/link accent in light and dark themes.

### Secondary

- **Amber** (`amber-50`–`amber-950`): existing warm yellow-orange scale, available for attention and warm emphasis. The semantic `warning` palette remains the status-role source.
- **Orange** (`orange-50`–`orange-950`): existing deeper orange scale for warm emphasis and data visualization; do not substitute it for semantic warning states without context.

### Neutral

- **Neutral** (`neutral-50`–`neutral-950`): primary UI-kit surface, text, border, and disabled-state scale.
- **Slate, gray, zinc, stone**: alternative neutral families for consumers; choose one family per surface instead of mixing nearly identical grays.
- **Semantic palettes** (`info`, `success`, `warning`, `danger`): status colors used by badges, alerts, and field validation.
- **Regional flag colors** (`flag-*`): isolated specialty tokens from `scss/_flags.scss`; use only for flag/region visuals.
- **Documentation surfaces** (`docs-light-*`, `docs-dark-*`): VitePress light/dark theme palette.

**The Source-Of-Truth Rule.** Use Sass tokens in `scss/_variables.scss` for framework colors; OKLCH values here are a readable, converted representation, not a replacement source of truth.

**The Warm Accent Rule.** Amber and orange are already available as complete eleven-step scales. Use their exact existing palette tokens rather than introducing duplicate aliases or one-off shades.

## Typography

**Display Font:** Inter where available, then system sans-serif (documentation theme).
**Body Font:** System sans-serif for UI-kit components; Inter with system fallbacks for VitePress.
**Label/Mono Font:** Platform monospace stacks.

**Character:** Compact, familiar system typography keeps a utility library legible across host applications. The docs use Inter for reading and a native monospace stack for code.

### Hierarchy

- **UI-kit controls** (14px, 600 weight, 20px line-height): button labels; small variant is 13px and large is 16px.
- **Fields** (14px, 500 label weight): labels and input text.
- **Documentation body** (Inter/system sans-serif): inherited VitePress hierarchy.
- **Code** (monospace): API examples and technical identifiers.

## Layout

The Sass package exports a 4px-based spacing scale and standard breakpoints at 640, 768, 1024, 1280, 1536, and 1920px. UI components use compact spacing: 8px vertical and 16px horizontal for medium buttons, 8px/12px for inputs, and 20px for card content. Documentation layout follows VitePress responsive containers and navigation.

## Elevation & Depth

The system uses a restrained hybrid: borders and tonal surface changes establish hierarchy; the Sass scale supplies subtle shadows for elevated cards and overlays. Reserve elevation for elements that need separation rather than applying it to every surface.

### Shadow Vocabulary

- **Default** (`--shadow-default`): low-contrast separation for standard raised elements.
- **Small / medium / large / extra-large** (`--shadow-sm` through `--shadow-xl`): progressively elevated overlays and cards.
- **2XL / inner** (`--shadow-2xl`, `--shadow-inner`): strong overlay depth and inset treatment when needed.

## Shapes

The UI kit uses gently rounded, small-to-medium corners: 6px for buttons, inputs, and alerts; 8px for cards; full radius for badges and circular loading indicators. Borders are thin and tonal rather than decorative. The complete exported radius scale is in the frontmatter.

## Components

### Buttons

- **Primary:** Purple 600 background with neutral 50 text; purple 700 on hover. Medium size uses 8px × 16px padding.
- **Secondary:** Neutral 100 surface and neutral 900 text, shifting to neutral 200 on hover.
- **Ghost:** Transparent at rest with neutral 700 text; neutral 100 hover surface.
- **Danger:** Danger 600 with neutral 50 text, shifting to danger 700 on hover.
- **Focus / disabled:** 2px purple 500 focus outline with 2px offset; disabled controls reduce opacity to 55% and use a not-allowed cursor.

### Chips

Badges use a full-pill silhouette with compact padding. Neutral, info, success, warning, and danger variants pair pale backgrounds with darker text from the same semantic family.

### Cards / Containers

Cards use neutral 50 surfaces, neutral 200 borders, 8px corners, and 20px body padding. Elevated cards replace the border with the medium shadow; headers and footers use tonal dividers and neutral surfaces.

### Inputs / Fields

Fields use neutral 50 backgrounds and borders, 6px corners, and a purple 500 focus border with a soft ring. Invalid fields use danger 500; disabled fields move to neutral 100 with muted text.

### Navigation

The docs navigation uses VitePress brand indigo and theme-provided light/dark text, border, and surface variables. Keep navigation states consistent with the active theme rather than hard-coding a second palette.

### Alerts

Info, success, warning, and danger alerts use their semantic 50 background, 200 border, and 800 foreground tokens, with 6px corners and compact 12px/16px padding.

## Do's and Don'ts

### Do:

- **Do** use the existing `orange-*` and `amber-*` scales when warm hues are needed.
- **Do** pair status colors with their semantic intent and use the matching light background/dark foreground family.
- **Do** preserve light/dark documentation token distinctions.
- **Do** use OKLCH values from this document as reference while retaining Sass as the source of truth.

### Don't:

- **Don't** modify source palette HSL values just to match rounded OKLCH documentation values.
- **Don't** use amber or orange as an interchangeable replacement for warning semantics.
- **Don't** mix multiple neutral families within one component or surface without a specific contrast reason.
- **Don't** use regional flag colors outside flag/region representations.
- **Don't** add a duplicate amber/orange scale: both already exist in the framework palette.
